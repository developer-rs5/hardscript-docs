HardScript is a language for writing backends: HTTP servers, WebSocket
endpoints, database access, scheduled work. You write one file, the compiler
emits a single C++ translation unit, and `hard build` produces a native
executable. There is no runtime to deploy, no garbage collector in the request
path, and no virtual machine between your code and the machine.

The compiler is in Rust. It lowers to C++ and shells out to `g++`, which means
the toolchain is one C++23 compiler away from a build — [`hard doctor`](/docs/tooling/cli)
checks that assumption rather than you finding out later.

## What a program looks like

A HardScript program is a set of module imports, a model, and some routes. This
is the whole thing — it compiles, and it serves:

```hard title=main.hard
bring http

bring json

app @8080

model User = users [
    id => Int #id,
    email => Email,
    name => Str,
]

GET "/users" :: {
    <- []
}

POST "/users" :: (body = User) {
    ?(body.email == "") {
        <- { status: 422, error: "email is required" }
    }
    <- { status: 201, user: { id: body.email, name: body.name } }
}
```

Four things to notice, because they are the shape of the whole language:

- `bring` imports a module. `http` gives routes, `json` gives parsing.
- `app @8080` declares the port, once, at the top level.
- A `model` is a declaration, not a class: a name, a table, and its fields.
- A route is `VERB "path" :: { }`. The body returns with `<-`, which reads as
  "respond with" and keeps the last expression from being ambiguous.

## What the compiler is strict about

Type errors, unknown fields, and malformed routes are all rejected before a
binary exists. Every diagnostic has a stable code — `HS0001` and upwards — and
the whole catalog is on one page: [error catalog](/docs/errors/catalog).

The strictness stops at the edges. Values crossing a route boundary are checked
structurally, and there is more than one way to write a model, which is a wart
rather than a philosophy: [models](/docs/orm/models) explains it.
